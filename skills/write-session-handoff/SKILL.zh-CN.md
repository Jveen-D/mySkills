# 编写会话交接文档

创建一份真实、最新的工作快照，并保存到 `HANDOFF.md`。文档应面向一个有能力接手、但无法访问当前会话内容的后续会话。

## 工作流程

1. 确定目标目录。
   - 优先使用当前 Git 仓库的根目录。
   - 否则使用当前任务或项目的根目录。
   - 如果不存在项目，则使用当前工作目录。
   - 写入 `<target>/HANDOFF.md`。

2. 根据证据还原当前状态。
   - 将当前请求和会话内容作为上下文。
   - 视情况检查已有的 `HANDOFF.md`、相关源码和任务文件、`git status`、当前分支与提交、差异、最近提交，以及现有测试或命令结果。
   - 明确区分已完成、进行中、计划中和受阻的工作。不要把意图描述成已经完成的事实。
   - 记录有助于下一会话恢复工作的准确文件路径、标识符、命令、错误和验证结果。
   - 明确说明不确定之处，不要猜测。

3. 更新交接文档。
   - 用当前快照替换过时状态；不要追加另一份相互冲突的交接内容。
   - 保留已有交接文档中仍然有效的决策、未解决的阻塞项和来之不易的避坑经验。
   - 使用与用户一致的工作语言。采用简洁、具体的表达，不要写成按时间顺序展开的流水账。
   - 绝不包含密码、凭据、令牌或不必要的个人数据。
   - 不要仅为准备交接而暂存、提交、还原或清理代码，也不要停止服务或进行其他项目改动。除非用户明确要求，否则只创建或更新 `HANDOFF.md`。

4. 验证结果。
   - 写入后重新读取 `HANDOFF.md`。
   - 删除占位符和过时表述。
   - 确保下列每个必需章节都存在；确实没有内容时，也要如实写明“无”或“当前没有已知阻塞”。
   - 在最终回复中链接该文件，并用一两句话概括最重要的当前状态。

## 必需格式

使用以下结构，并根据用户使用的语言调整标题：

```markdown
# HANDOFF

> 更新时间：YYYY-MM-DD HH:MM TZ

## 1. 任务

- 目标和预期结果
- 范围、约束和验收标准

## 2. 已完成

- 已完成的具体工作，以及相关文件或行为变化
- 验证命令及其结果

## 3. 当前状态与卡点

- 正在进行的工作，以及未提交或未验证的改动
- 准确的阻塞条件、错误、依赖或尚未作出的决定
- 与当前阻塞有关的失败尝试

## 4. 下一步计划

1. 第一个可直接执行的操作，包括应从哪个文件或命令开始
2. 按依赖顺序排列的后续操作
3. 最终验证或验收检查

## 5. 绝对不要再踩的坑

- 尝试过什么、为什么失败，以及正确或更安全的做法

## 6. 关键上下文

- 工作区或仓库根目录
- 分支和提交（如适用）
- 重要文件、决策、依赖、正在运行的服务和实用命令
```

下一步必须可直接执行，不能含糊。每个踩坑记录都要包含足够的原因和证据，以防重复犯错；不要为了填满章节而编造问题。
