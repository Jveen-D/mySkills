# 中文 Git 提交

## 工作流程

创建或建议提交信息时：

1. 先检查实际 diff，再决定提交信息。
2. 识别变更的主要意图，而不只是看被修改的文件。
3. 使用 `<type>: <中文摘要>` 格式。
4. 摘要要简洁、具体，并使用简体中文。
5. 摘要末尾不要加标点。
6. 只有在需要额外背景、迁移说明或风险说明时才添加正文。

当用户要求 Codex 执行 `git commit` 时，在完成任务所需的正常暂存与验证步骤后，使用选定的中文提交信息进行提交。

## 提交类型

使用以下类型：

- `feat`: 新增面向用户或开发者的能力。
- `fix`: 修复 bug、错误行为、崩溃、回归或异常边界情况。
- `style`: 只修改视觉/UI 样式、格式、空白、CSS 展示、文案布局或不影响行为的外观。
- `refactor`: 在不改变行为的前提下重构代码结构。
- `perf`: 改善运行性能、内存占用、包体积、查询效率或渲染速度。
- `docs`: 修改文档、作为文档存在的注释、README、指南、示例或生成文档。
- `test`: 仅新增、更新或修复测试、fixture、mock、snapshot 或测试基础设施。
- `chore`: 修改不影响应用行为的维护项，例如仓库清理、配置清理、元数据、编辑器设置或常规脚本。
- `build`: 修改构建系统、打包、bundle、锁文件、依赖版本或生成的构建产物。
- `ci`: 修改 CI/CD 工作流、自动化、发布流水线或仓库检查。
- `security`: 修复或加强安全行为、权限、校验、密钥处理、依赖漏洞或认证相关流程。
- `revert`: 回退之前的提交。
- `release`: 版本号、变更日志、发布元数据或发布准备。

## 选择规则

优先选择最能解释用户可见或系统可见结果的类型：

- 新功能加测试：使用 `feat`。
- bug 修复加测试：使用 `fix`。
- 不改变行为的代码清理加测试：使用 `refactor`。
- CSS 或纯视觉组件改动：使用 `style`。
- 依赖更新用于修复安全问题：若安全意图明确，使用 `security`；否则使用 `build`。
- 仅锁文件或包管理器元数据变更：使用 `build`。
- 仅工具配置变更：使用 `chore`，除非该工具属于 CI/CD（`ci`）或构建/打包输出（`build`）。
- 文档和代码一起修改：除非文档是主要改动，否则使用代码改动对应的类型。
- 多个互不相关的改动：优先拆成多个提交；如果无法拆分，选择主导意图。

## 信息风格

冒号后用中文摘要：

- `feat: 添加用户导出入口`
- `fix: 修复登录过期后的跳转错误`
- `style: 调整仪表盘卡片间距`
- `refactor: 简化订单状态计算逻辑`
- `perf: 减少列表重复渲染`
- `docs: 更新部署说明`
- `test: 补充支付失败用例`
- `chore: 清理无用开发配置`
- `build: 升级前端依赖版本`
- `ci: 调整发布工作流触发条件`
- `security: 加强回调地址校验`
- `revert: 回退订单导出改动`
- `release: 准备 1.4.0 发布`

避免含糊的摘要，例如：

- `fix: 修复问题`
- `feat: 更新功能`
- `chore: 修改代码`

## 可选作用域

只有在能让 Git 历史更易扫描时才使用可选 scope：

- `feat(auth): 添加短信验证码登录`
- `fix(api): 修复分页参数解析`
- `style(button): 调整禁用态颜色`

当 scope 指代包、模块或文件夹时，保持小写 ASCII。

## 提交正文

必要时添加正文：

```text
fix: 修复批量导入失败后的状态回滚

导入过程中任一行校验失败时，现在会回滚已写入的临时记录，并保留失败原因供前端展示。
```

对于破坏性变更，添加 footer：

```text
feat: 调整任务同步接口参数

BREAKING CHANGE: /api/tasks/sync 现在要求传入 workspaceId。
```
